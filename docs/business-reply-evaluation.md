# 业务回复验收

平台的统一表达规范负责指导智能体说清结果。验收工具负责发现已知回归，不能替代核对工具结果，更不能把模型声称“完成”当作完成证据。

场景文件是 `qa/response-quality-20261029/cases.json`，包含 20 个中文业务场景。每项列出员工问题、真实执行证据、必须保留的事实、禁止的虚假成功、技术字段白名单及合格/不合格示例。示例是人工编写的测试数据，不是真实模型表现记录。

## 使用

把待验收的回复存为 JSON 数组或 JSONL。每条至少有 `caseId` 和原始 `reply`，可以补充 `runId`、`model` 便于对照真实运行。不要手工把回复改成示例后再评分。

```json
{"caseId":"invalid-container-digit","reply":"箱号最后一位可能有误。MSKU1234560 的校验未通过，末位应为 5，请核对原单。","runId":"隔离测试运行编号"}
```

```powershell
node scripts/evaluate-business-replies.mjs --input qa/response-quality-20261029/replies.jsonl --output qa/response-quality-20261029/report.json
node --test test/response-quality.test.mjs
```

可用 `--cases 自定义场景.json` 指定岗位自己的验收集。输入文件不提供时，工具会报错，不会自动以示例生成一份“模型通过”报告。`--output` 不能覆盖输入或场景文件。

报告逐项记录：必需事实、禁止结论、语境内的技术字段、重复长段落，以及明显密钥。`checkScore` 只是已配置规则的通过比例。`checks_passed` 表示这些规则没有发现错误；所有记录的 `reviewRequired` 始终为 `true`。返回码 `0` 表示离线错误检查通过，`1` 表示存在不合格回复，`2` 表示参数或文件错误。

技术语境按问题决定，不按管理员或员工身份决定。员工查业务时不应看到 `stdout`、`trackingActions` 等字段；管理员明确查询日志或要求编程时，可以保留完成任务必需的字段和代码。`allowedTechnicalTerms` 列出允许字段，`allowCodeBlocks` 明确允许代码块；技术内容也不能捏造已经执行。特殊诊断可用 `local-paths`、`sql` 作为对应类别的白名单标记。

篇幅超出场景的 `softMaxChars`、结论没有在开头出现，只产生人工复核提示。工具不会删字、改写、截断回复，也不会为了短句牺牲箱号、金额、币种、日期或失败事实。重复检查只检查较长的同文句段，普通短句不会被强制去重。

## 人工校准

1. 先核对执行证据：实际是否调用工具、是否写入成功、是否真的发送附件、当前权限是什么。运行状态、业务成功和投递状态分别检查。
2. 请熟悉岗位的员工直接阅读回复，指出“不知道办好没有”“下一步不明确”“专业字段看不懂”的具体句子。管理员身份不能替代普通员工的可读性判断。
3. 事实检查以原始单据和工具结果为准。号码、金额、日期、币种、范围及部分失败不能为简洁而遗漏。补充材料或资料冲突时允许提出必要问题。
4. 对误报先修正规则或白名单，再重新评分。例如“不能确认真实存在”不应被当作确认存在。不要要求模型绕过规则迎合关键词；否定、隐含承诺、遗漏和多轮指代仍需人工判断。
5. 新增真实问题的脱敏样本，并保留合格与不合格对照。修改模型、技能或岗位配置后重跑同一组场景；不要只保留通过样本。报告中注明模型、测试环境和证据位置，避免把人工示例测试混成线上业务验证。

建议先让每个岗位补齐约 20 个常见问题，覆盖正常、缺资料、失败、部分完成、附件和多轮追问。平台规则测试用于防止程序回归，隔离环境的真实模型运行用于检查生成行为，员工抽检用于检验最终业务表达，三者分别记录。
